# File Sizes Skill

## Назначение

Ограничивает размер файлов и задаёт обязательные правила разбиения.

## Лимиты

| Тип файла | Жёсткий максимум | Рекомендуемо |
|---|---:|---:|
| React/Vue component | 420 | 150-250 |
| Service / controller | 420 | 200-350 |
| Model / entity | 200 | 100-150 |
| Utility / helper | 150 | 50-100 |
| Test file | 500 | 200-300 |
| Config file | 100 | 50-80 |
| UI-kit / design-system barrel | 1000 | 500-800 |
| Shared CSS / style tokens | 1000 | 400-700 |
| Declarative schema / route / registry | 1000 | 300-700 |
| Fixture / localization / snapshot data | 1000 | 300-800 |
| Generated file | source-defined | source-defined |

Исключение `UI-kit / design-system barrel` применяй только к одному файлу с маленькими презентационными компонентами/стилевыми примитивами без бизнес-логики, данных, сетевых запросов и сложного состояния. Такой файл лучше секционировать заголовками, чем дробить на десятки файлов ради лимита `350`.

Исключение `Shared CSS / style tokens` применяй к файлам с design tokens, CSS custom properties, base/reset, layout primitives, utilities и общими visual primitives. Не применяй его к page-specific стилям, состоянию фичи или цепочкам overrides.

Исключение `Declarative schema / route / registry` применяй к API schemas, route maps, validation maps, enum/constant tables, DI registries, CLI command tables и другим файлам, где ценность именно в едином источнике правды. Не применяй к service/controller/resolver/job/workflow файлам с ветвлениями, I/O, состоянием и несколькими доменами.

Исключение `Fixture / localization / snapshot data` применяй к данным, которые проще читать/искать вместе. Если файл перестал быть таблицей данных и получил логику, он снова считается обычным code file.

`Generated file` не режется вручную по лимиту. Меняй source input и команду генерации; если ручная правка неизбежна, зафиксируй почему.

## Когда файл уже слишком большой

Считай файл проблемным, если есть одно или больше:

- больше `350` строк кода без комментариев — review-trigger, не автоматический split
- `350-420` строк допустимо не резать, если у файла одна ответственность, понятные секции и нет роста монолита
- больше `420` строк кода без комментариев — split по ответственности, кроме явного исключения
- больше `20` импортов
- несколько несвязанных концепций
- сложно быстро найти нужную функцию
- за `30` секунд нельзя понять назначение файла

## Обязательные действия

1. Разбери структуру файла.
2. Сгруппируй связанные функции.
3. Вынеси отдельные ответственности в отдельные модули.
4. Не создавай файлы на `10` строк только ради счётчика; новая единица должна иметь явную ответственность.
5. Зафиксируй разбиение рефакторингом, а не косметикой.

## Стратегии разбиения

- По ответственности (`SRP`): CRUD, auth, email, validation и т.д. не живут в одном сервисе без сильной причины.
- По feature: крупный UI или feature-директория режется на screen/container, подкомпоненты и hooks.
- Единый UI-kit/design-system файл не режется только из-за длины, если секции независимы и быстро находятся поиском.
- Общий CSS/style файл не режется только из-за длины, если это токены/база/утилиты/примитивы с низкой специфичностью и понятными секциями.
- Декларативный schema/route/registry файл не режется только из-за длины, если это единый источник правды и секции быстро находятся поиском.
- По слоям: route/controller/service/validation/dto не сливаются в один файл без сильной причины.
- По функциональной группе: `utils.ts` режется на `date.ts`, `validation.ts`, `function.ts`, `object.ts` и т.п.

## React / UI триггеры

Компонент почти наверняка монолитен, если там одновременно:

- `10+` состояний
- `5+` `useEffect`
- `20+` обработчиков
- `200+` строк JSX

В таком случае выноси:

- подкомпоненты по секциям интерфейса
- hooks для загрузки данных и побочных эффектов
- отдельные action/helper/validation модули

## Backend триггеры

Сервис почти наверняка монолитен, если в одном классе/файле живут несвязанные блоки вроде:

- CRUD
- auth/token logic
- profile/media handling
- social/integration logic
- notifications

Режь по ответственности на отдельные сервисы.

## Тесты

- Большой test file тоже режется по функциональности или сценариям.
- Один тестовый файл на `50+` тестов или на несколько независимых тем — сигнал к разбиению.

## Checklist

- файл меньше жёсткого лимита?
- у файла одна чёткая ответственность?
- все функции связаны между собой?
- импортов меньше `20`?
- назначение файла понятно за `30` секунд?
- дублирование устранено без лишних абстракций?

## Исключения

Лимит можно превысить только для:

- generated code
- config files
- migration files
- UI-kit / design-system barrel без бизнес-логики
- Shared CSS / style tokens с низкой специфичностью
- Declarative schema / route / registry как единый источник правды
- Fixture / localization / snapshot data с табличными/поисковыми данными

Даже тогда нужно:

- задокументировать, почему файл большой
- проверить, нельзя ли всё же разделить
- добавить навигационные комментарии, если это реально помогает
